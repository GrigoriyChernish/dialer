# Сигналізація

Контракт між клієнтом (віджет) і сервером: виклик, відповідь, «зайнято», таймаути та обмін станом під час розмови.
Медіа йдуть через LiveKit, сигналізація ні. Огляд архітектури в [architecture.md](architecture.md),
стани дзвінка на клієнті в [demo.md](demo.md).

Джерело правди для типів: `packages/shared/src/signaling.ts`. Цей документ описує поведінку, а типи
мають з ним збігатися; при розбіжності виправляємо обидва в одному коміті.

## Принципи
- **Стан дзвінка належить серверу.** Клієнт надсилає наміри (`call.invite`, `call.accept`), сервер вирішує
  й розсилає результат. Клієнт не переходить у `ringing` чи `connected`, доки сервер цього не підтвердив.
- **Таймери рахує сервер.** Клієнт показує відлік за `expiresAt`, але сам дзвінок не завершує.
- **Медіа окремо.** Мікрофон, камера, якість і відновлення з'єднання клієнт бере з LiveKit.
  Через сигналізацію йде лише те, чого LiveKit не знає: утримання.
- **Один транспорт.** Усе, включно з контактами й історією, приходить тим самим WebSocket.

## Транспорт
- `wss://<домен>/ws`. Токен в URL не передаємо, щоб він не потрапляв у логи: перший кадр клієнта це `hello`.
- Кадри текстові, JSON. Максимальний розмір 16 КБ.
- Якщо `hello` не надійшов за 5 с, сервер закриває з'єднання кодом `4401`.
- `ping` від клієнта кожні 25 с. Якщо від клієнта 60 с тиші, сервер закриває з'єднання.
- Перепідключення з експоненційною паузою 1, 2, 4, 8, 15 с (далі 15 с) і випадковим зсувом до 30%.

## Формат повідомлень
```ts
type Frame = {
  v: 1;              // версія протоколу
  type: string;      // «call.invite», «call.incoming» …
  id?: string;       // клієнт → сервер: ідентифікатор запиту (UUID)
  reqId?: string;    // сервер → клієнт: на який запит це відповідь
  // решта полів залежить від type
};
```
- Кожен запит клієнта з `id` отримує рівно одну відповідь: `ack` або `error` з тим самим `reqId`.
- Повторний запит з тим самим `id` не виконується вдруге: сервер повертає попередню відповідь.
  Це робить безпечним повтор після обриву.
- Події сервера без `reqId` надходять у порядку виникнення. Їм не потрібне підтвердження.
- Невідомі `type` і поля клієнт ігнорує. Сервер на невідомий `type` відповідає `error` з кодом `unknown_type`.

## Ідентифікатори
| Поле | Що це |
|---|---|
| `userId` | стабільний ідентифікатор користувача. Для демо це номер E.164, `+380XXXXXXXXX` |
| `deviceId` | вкладка чи пристрій. Генерує клієнт, зберігає в `localStorage` віджета |
| `callId` | створює сервер під час `call.invite` (ULID). Він же назва кімнати LiveKit |

## Підключення

### `hello` (клієнт → сервер)
```json
{ "v": 1, "type": "hello", "id": "…", "token": "<токен користувача>", "deviceId": "d_7f3a", "locale": "uk" }
```
Відповідь `hello.ok`:
```json
{
  "v": 1, "type": "hello.ok", "reqId": "…",
  "user": { "userId": "+380501112233", "name": "Ірина" },
  "serverTime": 1790000000000,
  "activeCall": null,
  "contacts": [{ "userId": "+380671234567", "name": "Олена", "online": true }],
  "recents": [{ "callId": "…", "peer": "+380671234567", "direction": "out", "result": "completed", "startedAt": 1790000000000, "duration": 184 }]
}
```
- `serverTime` потрібен, щоб клієнт переводив `expiresAt` у локальний час.
- `activeCall` не `null`, якщо користувач має дзвінок у процесі (після перезавантаження сторінки або обриву зв'язку):
  клієнт відновлює екран без додаткових подій, а наступні зміни приходять як зазвичай. Якщо це `ringing`/`incoming`, у ньому
  є `expiresAt`; якщо `connected`, є `livekit` з новим токеном.
- Якщо токен недійсний або прострочений, відповідь `error` з кодом `token_invalid` чи `token_expired`,
  і сервер закриває з'єднання кодом `4401`. Віджет у відповідь надсилає хосту подію `token:expired`.

### `token.expiring` (сервер → клієнт)
За 60 с до кінця токена. Віджет просить у хоста новий (`token:expired` → `setToken`) і надсилає `auth.refresh`
(`{ token }`). Дзвінок під час оновлення токена не переривається.

## Дзвінок

### Поля `call`
```ts
type CallInfo = {
  callId: string;
  direction: 'out' | 'in';
  peer: { userId: string; name: string };
  state: 'ringing' | 'connected';
  expiresAt?: number;    // лише для ringing: час завершення очікування, мс
  startedAt?: number;    // лише для connected: момент відповіді
  livekit?: { url: string; token: string };   // лише для connected
};
```

### Команди клієнта
| `type` | Поля | Коли дозволено | Що відбувається |
|---|---|---|---|
| `call.invite` | `to: userId`, `video: boolean` | користувач вільний | сервер створює дзвінок і дзвонить усім пристроям адресата |
| `call.cancel` | `callId` | ми викликаємо, ще `ringing` | дзвінок завершується з `cancelled` |
| `call.accept` | `callId` | нам дзвонять, `ringing` | дзвінок стає `connected`, обидві сторони отримують токен LiveKit |
| `call.reject` | `callId` | нам дзвонять, `ringing` | дзвінок завершується з `rejected` |
| `call.hangup` | `callId` | `connected` | дзвінок завершується з `hangup` |
| `call.hold` | `callId`, `hold: boolean` | `connected` | сервер пересилає співрозмовнику `call.peer` |

`ack` на `call.invite` містить `{ call: CallInfo }`. На решту команд це порожній `ack`.

### Події сервера
| `type` | Кому | Поля |
|---|---|---|
| `call.ringing` | тому, хто дзвонить | `call` (стан `ringing`, `expiresAt`). Надсилається, коли хоча б один пристрій адресата отримав виклик |
| `call.incoming` | усім пристроям адресата | `call` (`direction: 'in'`, `expiresAt`) |
| `call.connected` | обом сторонам | `call` (стан `connected`, `livekit`) |
| `call.ended` | усім пристроям обох сторін | `callId`, `reason`, `duration?` |
| `call.peer` | співрозмовнику | `callId`, `hold: boolean` |

### Причини завершення (`reason`)
| Значення | Кому що означає | Запис в історії |
|---|---|---|
| `hangup` | хтось завершив розмову | `completed` у обох |
| `cancelled` | той, хто дзвонив, скасував до відповіді | вихідний `cancelled`, у адресата `missed` |
| `rejected` | адресат відхилив | вихідний `rejected`, у адресата `rejected` |
| `busy` | адресат зайнятий | вихідний `busy`, у адресата запису немає |
| `timeout` | ніхто не відповів за 60 с | вихідний `no_answer`, у адресата `missed` |
| `offline` | адресата немає в мережі й пуш не доставлено (або пуші не підписані) | вихідний `no_answer`, у адресата `missed` |
| `answered_elsewhere` | інший пристрій цього ж користувача прийняв або відхилив | окремого запису немає: дзвінок записується один раз, за результатом на пристрої, що відповів |
| `lost` | з'єднання втрачено й не відновилося | `completed` з фактичною тривалістю |
| `error` | збій сервера чи LiveKit | `failed` |

Відображення на екрани демо: `busy` → «Зайнято», `timeout`/`offline` → «Без відповіді»,
`cancelled` у адресата → «Пропущений дзвінок».

### Машина станів на сервері
```
  invite ──▶ ringing ──accept──▶ connected ──hangup / lost──▶ ended
                │
                └── cancel / reject / timeout / busy / offline ──▶ ended
```
`ended` кінцевий: нова спроба це новий `call.invite` з новим `callId`. Після завершення дзвінок у пам'яті сервера
тримається ще 30 с, щоб відповідати на запізнілі команди кодом `call_ended`, далі видаляється.

### Правила
- **Один дзвінок на користувача.** Якщо в користувача є дзвінок у стані `ringing` (будь-який напрям) або `connected`,
  новий `call.invite` до нього завершується з `busy`, а його власний `call.invite` відхиляється помилкою `already_in_call`.
  Другий вхідний під час розмови (пункт 3 беклогу) додасть подію `call.waiting` у версії 2.
- **Кілька пристроїв.** `call.incoming` іде на всі пристрої адресата. Перший `call.accept` виграє, решта пристроїв
  отримують `call.ended` з `answered_elsewhere`. Запізніла `call.accept` з іншого пристрою отримує помилку `call_ended`.
  Пристрій, який дзвонить, теж один: дзвінок прив'язаний до `deviceId` з `call.invite`.
- **Виклик самому собі** відхиляється помилкою `invalid_target`.
- **Таймаут.** 60 с від моменту створення. Цей час сервер віддає як `expiresAt`, клієнт не має власного таймера на завершення.
- **Кінець розмови.** Якщо з'єднання сигналізації одного з учасників обірвалося під час `connected`, дзвінок триває,
  доки LiveKit показує його в кімнаті. Коли в кімнаті лишається менше двох учасників довше за 30 с
  (вебхук LiveKit `participant_left`), сервер завершує дзвінок з `lost`.
- **Вхідний, коли пристрій офлайн.** Сервер одразу створює дзвінок і надсилає Web Push із `callId`. Якщо користувач
  підключився до закінчення таймаута, `hello.ok` містить `activeCall`, і віджет показує вхідний. Інакше `timeout`/`offline`.
  Без підписки на пуші й без жодного онлайн-пристрою одразу `offline`.
- **Демо-співрозмовники** (Олена, Андрій, Support) це серверні боти зі сценаріями з [demo.md](demo.md): відповідають через
  3,5 с, одразу дають `busy` або не відповідають. Для клієнта вони нічим не відрізняються від людей.

## Обмін станом під час розмови
| Що | Звідки | Як |
|---|---|---|
| Мікрофон, камера співрозмовника | LiveKit | події треків `TrackMuted`/`TrackUnmuted` |
| Якість сигналу | LiveKit | `ConnectionQualityChanged` |
| Відновлення з'єднання | LiveKit | `Reconnecting`/`Reconnected` |
| Співрозмовник зник | LiveKit | `ParticipantDisconnected` (дзвінок ще живий, бо діє 30-секундне вікно) |
| Утримання | сигналізація | `call.hold` → `call.peer` |

Утримання йде через сервер, бо LiveKit не має такого поняття: клієнт, якого тримають, лише глушить звук і
показує екран «Вас тримають». Сервер зберігає останнє значення в дзвінку, тож після перепідключення воно
повертається в `activeCall.peerHold`.

## Контакти, присутність, історія
| `type` | Напрям | Поля | Коли |
|---|---|---|---|
| `presence` | сервер → клієнт | `userId`, `online` | хтось з контактів підключився чи відключився |
| `contacts.update` | сервер → клієнт | `upsert: Contact[]`, `remove: userId[]` | у демо: хтось увійшов |
| `recents.add` | сервер → клієнт | `entry` | дзвінок завершився, запис додається одразу |
| `recents.seen` | клієнт → сервер | `upTo: timestamp` | користувач відкрив вкладку «Недавні», лічильник пропущених скидається |

Повний список контактів і історія приходять у `hello.ok`. Окремого HTTP-запиту на них немає.

## Web Push
Сервер надсилає пуш лише коли в адресата немає онлайн-пристроїв. Тіло:
```json
{ "type": "call.incoming", "callId": "…", "from": { "userId": "+380…", "name": "Олена" }, "expiresAt": 1790000060000 }
```
Сервер надсилає ще один пуш `{ "type": "call.ended", "callId": "…" }`, коли дзвінок закінчився до відповіді,
щоб воркер прибрав сповіщення. Дії «Відповісти» й «Відхилити» відкривають сторінку сайту
з віджетом, який сам надсилає `call.accept` чи `call.reject` після `hello`. Підписки зберігаються командою
`push.subscribe` (`{ subscription }`) і видаляються `push.unsubscribe`.

## Помилки
```json
{ "v": 1, "type": "error", "reqId": "…", "code": "already_in_call", "message": "Finish the current call first" }
```
`message` для логів, а не для показу користувачеві: тексти для людей живуть у `vue-i18n` за `code`.

| `code` | Значення |
|---|---|
| `token_invalid`, `token_expired` | токен не пройшов перевірку (закриває з'єднання) |
| `unknown_type` | невідомий `type` |
| `bad_request` | не пройшла валідація полів |
| `unsupported_version` | сервер не підтримує `v` з `hello` (закриває з'єднання) |
| `invalid_target` | адресата немає або це сам користувач |
| `already_in_call` | у користувача вже є дзвінок |
| `call_not_found` | невідомий `callId` |
| `call_ended` | дзвінок уже завершено |
| `not_allowed` | команда неможлива в поточному стані або для цього учасника |
| `rate_limited` | забагато запитів: не більше 10 `call.invite` за хвилину на користувача |
| `internal` | збій сервера |

## Приклади

### Успішний дзвінок
```
Ірина                      Сервер                       Олена
  │ call.invite(to=Олена) ──▶│                             │
  │◀── ack {call}            │── call.incoming ───────────▶│
  │◀── call.ringing          │                             │
  │                          │◀──────────── call.accept ───│
  │◀── call.connected ───────│── call.connected ──────────▶│
  │        (обидва підключаються до кімнати LiveKit за токеном)
  │ call.hangup ────────────▶│── call.ended(hangup) ──────▶│
  │◀── call.ended(hangup)    │                             │
```

### Без відповіді
```
Ірина                      Сервер                       Олена
  │ call.invite ────────────▶│── call.incoming ───────────▶│
  │◀── call.ringing          │          (60 с тиші)        │
  │◀── call.ended(timeout)   │── call.ended(timeout) ─────▶│
```

### Два пристрої адресата
```
Олена (вкладка A)          Сервер                   Олена (вкладка B)
  │◀── call.incoming ────────│── call.incoming ───────────▶│
  │                          │◀───────────── call.accept ──│
  │◀── call.ended(answered_elsewhere) ─│── call.connected ─▶│
```

## Відповідність дій клієнта
| Дія в `useCallStore` | Команда | Очікуваний стан |
|---|---|---|
| `call(contactId)` | `call.invite` | `ringing` після `ack`, далі `connected` чи `idle` з результатом |
| `cancel()` | `call.cancel` | `idle` після `call.ended` |
| `accept()` | `call.accept` | `connected` після `call.connected` |
| `reject()` | `call.reject` | `idle` |
| `hangup()` | `call.hangup` | `idle` після `call.ended` |
| `toggleHold()` | `call.hold` | `hold` одразу локально, підтверджується `ack` |

Перехід стору відбувається від подій сервера, а не від власних команд. Виняток: `hold`, бо він локальний і не
змінює стан дзвінка, а при `error` клієнт його відкочує.

## Версіонування
- Поле `v` це версія протоколу. Додавання нових подій і необов'язкових полів не піднімає версію.
- Несумісну зміну робимо як `v: 2`: сервер якийсь час приймає обидві версії, вибір за `v` у `hello`.
- Клієнт, який отримав `error` з кодом `unsupported_version`, показує хосту подію `error` і не перепідключається.

## Відкриті питання
- **Валідація.** Описати типи в `packages/shared` як TypeScript чи як схему (zod), з якої виводяться типи й валідація на сервері.
  Схема дасть перевірку вхідних кадрів безкоштовно, але це нова залежність.
- **Другий вхідний під час розмови** (`call.waiting`) і його дії з пункту 3 беклогу.
- **Групові дзвінки.** Тут не розглядаємо: кімната LiveKit на двох, контракт розрахований на двох учасників.
- **Кілька інстансів сервера.** Поки присутність і активні дзвінки в пам'яті одного процесу. Для масштабування
  знадобиться спільне сховище (Redis) і маршрутизація подій між інстансами.
