# Сигналізація

Контракт між клієнтом (віджет) і сервером: виклик, відповідь, «зайнято», таймаути та обмін станом під час розмови.
Медіа йдуть через LiveKit, сигналізація ні. Огляд архітектури в [architecture.md](architecture.md),
стани дзвінка на клієнті в [demo.md](demo.md).

Джерело правди для типів: `packages/shared/src/signaling.ts`. Цей документ описує поведінку, а типи
мають з ним збігатися; при розбіжності виправляємо обидва в одному коміті.

## Принципи
- **Стан дзвінка належить серверу.** Клієнт надсилає наміри (`call.invite`, `call.accept`), сервер вирішує
  й розсилає результат. Клієнт не переходить у `ringing` чи `connected`, доки сервер цього не підтвердив.
- **Таймери рахує сервер.** Клієнт показує відлік за `expiresAt`, але сам дзвінок не завершує.
- **Медіа окремо.** Мікрофон, камера, якість і відновлення з'єднання клієнт бере з LiveKit.
  Через сигналізацію йде лише те, чого LiveKit не знає: утримання.
- **Один транспорт.** Усе, включно з контактами й історією, приходить тим самим WebSocket.

## Транспорт
- `wss://<домен>/ws`. Токен в URL не передаємо, щоб він не потрапляв у логи: перший кадр клієнта це `hello`.
- Кадри текстові, JSON. Максимальний розмір 16 КБ.
- Якщо `hello` не надійшов за 5 с, сервер закриває з'єднання кодом `4401`.
- Коди закриття: `4401` немає `hello` вчасно чи токен недійсний, `4403` користувача заблоковано, `4426` непідтримувана версія протоколу `v`.
- `ping` від клієнта кожні 25 с, сервер відповідає `pong`. Якщо від клієнта 60 с тиші, сервер закриває з'єднання.
- Перепідключення з паузою 1, 1, 2, 3, 5 с (далі 5 с) і випадковим зсувом до 30%: перезапуск сервера при деплої на Fly.io триває ~10 с,
  тож клієнт повертається за кілька секунд після старту. Коли повертається мережа (`online`) чи вкладка знову видима, клієнт пробує одразу.

## Формат повідомлень
```ts
type Frame = {
  v: 1;              // версія протоколу
  type: string;      // «call.invite», «call.incoming» …
  id?: string;       // клієнт → сервер: ідентифікатор запиту (UUID)
  reqId?: string;    // сервер → клієнт: на який запит це відповідь
  // решта полів залежить від type
};
```
- Кожен запит клієнта з `id` отримує рівно одну відповідь: `ack` або `error` з тим самим `reqId`.
- Повторний запит з тим самим `id` не виконується вдруге: сервер повертає попередню відповідь.
  Це робить безпечним повтор після обриву.
- Події сервера без `reqId` надходять у порядку виникнення. Їм не потрібне підтвердження.
- Невідомі `type` і поля клієнт ігнорує. Сервер на невідомий `type` відповідає `error` з кодом `unknown_type`.

## Ідентифікатори
| Поле | Що це |
|---|---|
| `userId` | стабільний ідентифікатор користувача. Для демо це номер E.164, `+380XXXXXXXXX` |
| `deviceId` | вкладка чи пристрій. Генерує клієнт, зберігає в `localStorage` віджета |
| `callId` | створює сервер під час `call.invite` (ULID). Він же назва кімнати LiveKit |

## Підключення

### `hello` (клієнт → сервер)
```json
{ "v": 1, "type": "hello", "id": "…", "token": "<токен користувача>", "deviceId": "d_7f3a", "locale": "uk" }
```
Відповідь `hello.ok`:
```json
{
  "v": 1, "type": "hello.ok", "reqId": "…",
  "user": { "userId": "+380501112233", "name": "Ірина" },
  "serverTime": 1790000000000,
  "settings": { "waiting": true, "dnd": false },
  "calls": [],
  "contacts": [{ "userId": "+380671234567", "name": "Олена", "online": true }],
  "recents": [{ "callId": "…", "peer": "+380671234567", "direction": "out", "result": "completed", "startedAt": 1790000000000, "duration": 184 }]
}
```
- `settings` це налаштування користувача, див. [Налаштування](#налаштування).
- `serverTime` потрібен, щоб клієнт переводив `expiresAt` у локальний час.
- `calls` містить дзвінки користувача в процесі (від 0 до 2; після перезавантаження сторінки або обриву зв'язку):
  клієнт відновлює екран без додаткових подій, а наступні зміни приходять як зазвичай. Якщо дзвінок `ringing`, у ньому
  є `expiresAt`; якщо `connected`, є `livekit` з новим токеном, а також `hold` і `peerHold`.
- Якщо токен недійсний або прострочений, відповідь `error` з кодом `token_invalid` чи `token_expired`,
  і сервер закриває з'єднання кодом `4401`. Віджет у відповідь надсилає хосту подію `token:expired`.

### `token.expiring` (сервер → клієнт)
За 60 с до кінця токена. Віджет просить у хоста новий (`token:expired` → `setToken`) і надсилає `auth.refresh`
(`{ token }`). Дзвінок під час оновлення токена не переривається. Якщо токен спливе без оновлення, відкрите з'єднання лишається
(дзвінок не обривається), але нове підключення вже потребує свіжого токена.

## Дзвінок

### Поля `call`
```ts
type CallInfo = {
  callId: string;
  direction: 'out' | 'in';
  peer: { userId: string; name: string };
  state: 'ringing' | 'connected';
  waiting?: boolean;     // лише для вхідного ringing: у користувача вже є розмова, див. «Другий вхідний»
  hold?: boolean;        // лише для connected: ми тримаємо співрозмовника
  peerHold?: boolean;    // лише для connected: співрозмовник тримає нас
  expiresAt?: number;    // лише для ringing: час завершення очікування, мс
  startedAt?: number;    // лише для connected: момент відповіді
  livekit?: { url: string; token: string };   // лише для connected
};
```

### Команди клієнта
| `type` | Поля | Коли дозволено | Що відбувається |
|---|---|---|---|
| `call.invite` | `to: userId`, `video: boolean` | користувач вільний | сервер створює дзвінок і дзвонить усім пристроям адресата |
| `call.cancel` | `callId` | ми викликаємо, ще `ringing` | дзвінок завершується з `cancelled` |
| `call.accept` | `callId`, `action?: 'hold' \| 'end'` | нам дзвонять, `ringing` | дзвінок стає `connected`, обидві сторони отримують токен LiveKit. `action` обов'язкове, якщо в користувача вже є розмова (`call.incoming` із `waiting: true`): `hold` утримує її, `end` завершує |
| `call.reject` | `callId` | нам дзвонять, `ringing` | дзвінок завершується з `rejected` |
| `call.hangup` | `callId` | `connected` | дзвінок завершується з `hangup` |
| `call.hold` | `callId`, `hold: boolean` | `connected` | сервер пересилає співрозмовнику `call.peer`. Якщо `hold: false` і в користувача є інша розмова без утримання, вона автоматично стає утримуваною (перемикання між дзвінками) |

`ack` на `call.invite` містить `{ call: CallInfo }`. На решту команд це порожній `ack`.

### Події сервера
| `type` | Кому | Поля |
|---|---|---|
| `call.ringing` | тому, хто дзвонить | `call` (стан `ringing`, `expiresAt`, `waiting`). Надсилається, коли хоча б один пристрій адресата отримав виклик. `waiting: true`: адресат на іншому дзвінку, клієнт показує «Абонент на іншому дзвінку» замість гудків |
| `call.incoming` | усім пристроям адресата | `call` (`direction: 'in'`, `expiresAt`, `waiting`) |
| `call.updated` | `hold`: усім пристроям користувача, який тримає (без пристрою, що дав команду); `waiting`: обом сторонам дзвінка | `callId` і змінені поля: `hold`, `waiting`. Так інші пристрої й екран бачать утримання, перемикання та кінець очікування |
| `call.connected` | обом сторонам | `call` (стан `connected`, `livekit`) |
| `call.ended` | усім пристроям обох сторін | `callId`, `reason`, `duration?` |
| `call.peer` | співрозмовнику | `callId`, `hold: boolean` |

### Причини завершення (`reason`)
| Значення | Кому що означає | Запис в історії |
|---|---|---|
| `hangup` | хтось завершив розмову | `completed` у обох |
| `cancelled` | той, хто дзвонив, скасував до відповіді | вихідний `cancelled`, у адресата `missed` |
| `rejected` | адресат відхилив | вихідний `rejected`, у адресата `rejected` |
| `busy` | адресат зайнятий | вихідний `busy`, у адресата запису немає. Виняток: `busy` через `settings.dnd` чи вимкнене `settings.waiting` дає адресату тихий `missed`, див. [Налаштування](#налаштування) |
| `timeout` | ніхто не відповів за 60 с | вихідний `no_answer`, у адресата `missed` |
| `offline` | адресата немає в мережі й пуш не доставлено (або пуші не підписані) | вихідний `no_answer`, у адресата `missed` |
| `answered_elsewhere` | інший пристрій цього ж користувача прийняв або відхилив | окремого запису немає: дзвінок записується один раз, за результатом на пристрої, що відповів |
| `lost` | з'єднання втрачено й не відновилося | `completed` з фактичною тривалістю |
| `error` | збій сервера чи LiveKit | `failed` |

Відображення на екрани демо: `busy` → «Зайнято», `timeout`/`offline` → «Без відповіді»,
`cancelled` у адресата → «Пропущений дзвінок».

### Машина станів на сервері
```
  invite ──▶ ringing ──accept──▶ connected ──hangup / lost──▶ ended
                │
                └── cancel / reject / timeout / busy / offline ──▶ ended
```
`ended` кінцевий: нова спроба це новий `call.invite` з новим `callId`. Після завершення дзвінок у пам'яті сервера
тримається ще 30 с, щоб відповідати на запізнілі команди кодом `call_ended`, далі видаляється.

### Правила
- **Не більше двох дзвінків на користувача.** Другим може бути лише вхідний під час розмови, див. [Другий вхідний](#другий-вхідний-під-час-розмови).
  Якщо в користувача є дзвінок у стані `ringing` (будь-який напрям) або вже два дзвінки, новий `call.invite` до нього
  завершується з `busy`. Власний `call.invite` користувача, який уже в розмові, відхиляється помилкою `already_in_call`.
- **Кілька пристроїв.** `call.incoming` іде на всі пристрої адресата. Перший `call.accept` виграє, решта пристроїв
  отримують `call.ended` з `answered_elsewhere`. Запізніла `call.accept` з іншого пристрою отримує помилку `call_ended`.
  Пристрій, який дзвонить, теж один: дзвінок прив'язаний до `deviceId` з `call.invite`.
- **Виклик самому собі** відхиляється помилкою `invalid_target`.
- **Таймаут.** 60 с від моменту створення. Цей час сервер віддає як `expiresAt`, клієнт не має власного таймера на завершення.
- **Кінець розмови.** Якщо з'єднання сигналізації одного з учасників обірвалося під час `connected`, дзвінок триває,
  доки LiveKit показує його в кімнаті. Коли в кімнаті бракує когось із двох учасників довше за 30 с
  (вебхуки LiveKit `participant_joined`/`participant_left`/`room_finished`), сервер завершує дзвінок з `lost`. Відлік починається
  вже з `call.connected`, тож якщо учасники так і не зайшли в кімнату, дзвінок завершиться за 30 с. Для дзвінків із демо-ботами
  `lost` не діє. Завершений дзвінок закриває кімнату.
- **Токен кімнати** (`call.connected.call.livekit`, `hello.ok.calls[].livekit`) отримує лише пристрій, який бере участь у розмові:
  той, з якого дзвонили, і той, що прийняв. Інші пристрої користувача бачать дзвінок без `livekit`. Дзвінки з демо-ботами без `livekit`.
- **Вхідний, коли пристрій офлайн.** Сервер одразу створює дзвінок і надсилає Web Push із `callId`. Якщо користувач
  підключився до закінчення таймаута, `hello.ok` містить цей дзвінок у `calls`, і віджет показує вхідний. Інакше `timeout`/`offline`.
  Без підписки на пуші й без жодного онлайн-пристрою одразу `offline`.
- **Адресат, якому дзвінок не доставляли** (`busy`, `offline`), не отримує `call.ended`: подія йде лише тому, хто дзвонив. Запис `missed` для `offline` він бачить в історії.
- **Демо-співрозмовники** (Олена, Андрій, Support; `userId` `bot:olena`, `bot:andriy`, `bot:support`) це серверні боти зі сценаріями з [demo.md](demo.md): Олена відповідає через
  3,5 с, Андрій не відповідає, Support одразу дає `busy`. Для Андрія очікування коротше (8 с, `expiresAt` це відображає), щоб демо не чекало хвилину. Для клієнта вони нічим не відрізняються від людей.

## Обмін станом під час розмови
| Що | Звідки | Як |
|---|---|---|
| Мікрофон, камера співрозмовника | LiveKit | події треків `TrackMuted`/`TrackUnmuted` |
| Якість сигналу | LiveKit | `ConnectionQualityChanged` |
| Відновлення з'єднання | LiveKit | `Reconnecting`/`Reconnected` |
| Співрозмовник зник | LiveKit | `ParticipantDisconnected` (дзвінок ще живий, бо діє 30-секундне вікно) |
| Утримання | сигналізація | `call.hold` → `call.peer` |

Утримання йде через сервер, бо LiveKit не має такого поняття: клієнт, якого тримають, лише глушить звук і
показує екран «Вас тримають». Сервер зберігає останнє значення в дзвінку, тож після перепідключення воно
повертається в `calls[].peerHold`.

## Другий вхідний під час розмови
Користувач із розмовою (`connected`) може отримати ще один вхідний дзвінок. Це єдиний випадок, коли в нього буває два дзвінки.

**Коли дозволено.** У користувача рівно один дзвінок і він `connected` (утримуваний чи ні). Тоді:
- усім пристроям адресата йде `call.incoming` із `waiting: true`, а тому, хто дзвонить, `call.ringing` із `waiting: true`;
- усі пристрої адресата показують однакові три дії: «Утримати й прийняти», «Завершити й прийняти», «Відхилити»;
- таймаут 60 с, як у звичайному вхідному. Без відповіді дзвінок завершується з `timeout`, у адресата `missed`.

В інших випадках новий вхідний дає `busy`: дзвінок у `ringing` (будь-який напрям), вже два дзвінки або вимкнене
налаштування `waiting` (див. [Налаштування](#налаштування)).
Якщо перша розмова закінчилась, поки другий ще дзвонить, сервер надсилає `call.updated` із `waiting: false`,
і він стає звичайним вхідним.

**Дії.** Обираються полем `action` у `call.accept`, щоб вхід у новий дзвінок і зміна старого були одним атомарним запитом:

| Дія | `call.accept` | Що робить сервер |
|---|---|---|
| Утримати й прийняти | `action: 'hold'` | перша розмова отримує `hold: true` (співрозмовник бачить `call.peer`), другий дзвінок стає `connected` |
| Завершити й прийняти | `action: 'end'` | перша розмова завершується з `hangup`, другий дзвінок стає `connected` |
| Відхилити | `call.reject` | другий дзвінок завершується з `rejected`, перша розмова не змінюється |

`call.accept` без `action`, коли в користувача є розмова, дає `bad_request`. `action` без розмови ігнорується.
Демо-боти очікування не мають: бот, що вже розмовляє, відповідає `busy` на будь-який новий виклик.

**Перемикання.** Утримуваний дзвінок повертається командою `call.hold` із `hold: false`: поточна розмова за цю ж
транзакцію стає утримуваною. Обидва зміни розсилаються `call.updated`. Завершення активної розмови не знімає утримання
з іншої: користувач сам повертає її командою `call.hold`.

**Медіа.** Утримання не розриває кімнату LiveKit: обидва треки глушаться, учасник лишається в кімнаті. Тому правило
`lost` (30 с порожньої кімнати) не чіпає утримувані дзвінки, а другому дзвінку не потрібен другий `Room`.
Клієнт тримає окреме підключення до кожної кімнати; активним лишається лише те, що без `hold`.

```
Ірина (у розмові з Оленою)    Сервер                   Андрій
  │                              │◀── call.invite(to=Ірина)──│
  │◀── call.incoming (waiting) ──│── call.ringing(waiting) ─▶│
  │ call.accept(action=hold) ───▶│                           │
  │◀── call.updated(hold:true, Олена)                        │
  │                              │── call.peer(hold:true) ──▶ Олена
  │◀── call.connected ───────────│── call.connected ────────▶│
```

## Налаштування
Налаштування користувача зберігаються на сервері, бо частину рішень (наприклад, `busy` чи `waiting`) ухвалює сервер,
і вони однакові на всіх пристроях користувача.

```ts
type Settings = {
  waiting: boolean;   // true за замовчуванням: другий вхідний під час розмови дзвонить як «очікування»
  dnd: boolean;       // false за замовчуванням: «Не турбувати», усі вхідні отримують busy
};
```

| `type` | Напрям | Поля | Що відбувається |
|---|---|---|---|
| `settings.update` | клієнт → сервер | `settings: Partial<Settings>` | сервер зберігає змінені поля, відповідає `ack` з повним `settings` |
| `settings.updated` | сервер → клієнт | `settings: Settings` | усім іншим пристроям користувача, щоб перемикачі не розходилися |

Поточні значення приходять у `hello.ok`. Невідомі поля в `settings.update` сервер ігнорує,
значення неправильного типу дають `bad_request`. Нові налаштування додаються як необов'язкові поля без зміни `v`.

### `waiting: false` («Не дзвонити, коли я на дзвінку»)
- Якщо в адресата рівно один `connected` дзвінок і `settings.waiting === false`, `call.invite` до нього завершується з `busy`
  без `call.incoming` і `call.ringing`. Новий код причини не потрібен.
- Той, хто дзвонить, бачить звичайний екран «Зайнято».
- Адресат отримує **тихий пропущений**: запис історії `missed` з `silent: true` і подію `recents.add`. Він видно в «Недавніх»,
  але не збільшує лічильник непрочитаних пропущених. Звичайний `busy` (дзвінок у `ringing`, вже два дзвінки) запису не створює.
- Зміна налаштування діє лише на нові виклики. Другий дзвінок, який уже дзвонить як `waiting`, не скасовується.
- Демо-боти (Олена, Андрій, Support) поводяться за тим самим правилом, щоб сценарії демо збігалися з реальними.

### `dnd: true` («Не турбувати»)
Повністю вимикає вхідні, навіть коли користувач вільний.
- Будь-який `call.invite` до користувача завершується з `busy`. Жоден пристрій не отримує `call.incoming`, Web Push не надсилається.
- Той, хто дзвонить, бачить звичайне «Зайнято» і не може відрізнити це від справжньої зайнятості: стан «Не турбувати» не розкривається.
  Присутність (`presence`) теж його не показує.
- Адресат отримує тихий `missed` (`silent: true`), як і при `waiting: false`.
- Діє на нові виклики. Дзвінок, що вже дзвонить, і поточна розмова не змінюються.
- Власні виклики користувача працюють як зазвичай: режим блокує лише вхідні.
- `dnd` сильніший за `waiting`: поки `dnd` увімкнено, значення `waiting` нічого не змінює.
- Вимкнення автоматично за таймером у цій версії немає, користувач вимикає режим сам.
- Демо-боти (Олена, Андрій, Support) це користувачі, тож за замовчуванням `dnd: false`. Щоб перевірити сценарій «Не турбувати»
  на демо, потрібен другий справжній користувач.

### Порядок перевірок у `call.invite`
Сервер перевіряє по черзі й зупиняється на першому збігу:
1. Адресата немає або це сам користувач → `invalid_target`.
2. У того, хто дзвонить, уже є дзвінок → `already_in_call`.
3. Перевищено ліміт `call.invite` → `rate_limited`.
4. У адресата `dnd: true` → `busy` (тихий `missed`).
5. У адресата дзвінок у `ringing` або вже два дзвінки → `busy`.
6. У адресата один `connected` дзвінок: `waiting: false` → `busy` (тихий `missed`), інакше очікування (`waiting: true`).
7. Жодного онлайн-пристрою й немає пуш-підписки → `offline`.
8. Інакше звичайний дзвінок.

## Контакти, присутність, історія
| `type` | Напрям | Поля | Коли |
|---|---|---|---|
| `presence` | сервер → клієнт | `userId`, `online` | хтось з контактів підключився чи відключився |
| `contacts.update` | сервер → клієнт | `upsert: Contact[]`, `remove: userId[]` | у демо: хтось увійшов |
| `recents.add` | сервер → клієнт | `entry` | дзвінок завершився, запис додається одразу |
| `recents.seen` | клієнт → сервер | `upTo: timestamp` | користувач відкрив вкладку «Недавні», лічильник пропущених скидається. Ще не реалізовано: сервер відповідає `unknown_type` (беклог, пункт 13) |

Повний список контактів і історія приходять у `hello.ok`. Окремого HTTP-запиту на них немає.

## Web Push
Ще не реалізовано (беклог, пункт 15): зараз адресат не в мережі дає одразу `offline`. Сервер надсилатиме пуш лише коли в адресата немає онлайн-пристроїв і не ввімкнено `settings.dnd`. Тіло:
```json
{ "type": "call.incoming", "callId": "…", "from": { "userId": "+380…", "name": "Олена" }, "expiresAt": 1790000060000 }
```
Сервер надсилає ще один пуш `{ "type": "call.ended", "callId": "…" }`, коли дзвінок закінчився до відповіді,
щоб воркер прибрав сповіщення. Дії «Відповісти» й «Відхилити» відкривають сторінку сайту
з віджетом, який сам надсилає `call.accept` чи `call.reject` після `hello`. Підписки зберігаються командою
`push.subscribe` (`{ subscription }`) і видаляються `push.unsubscribe`.

## Помилки
```json
{ "v": 1, "type": "error", "reqId": "…", "code": "already_in_call", "message": "Finish the current call first" }
```
`message` для логів, а не для показу користувачеві: тексти для людей живуть у `vue-i18n` за `code`.

| `code` | Значення |
|---|---|
| `token_invalid`, `token_expired` | токен не пройшов перевірку (закриває з'єднання) |
| `unknown_type` | невідомий `type` |
| `bad_request` | не пройшла валідація полів |
| `unsupported_version` | сервер не підтримує `v` з `hello` (закриває з'єднання) |
| `invalid_target` | адресата немає або це сам користувач |
| `already_in_call` | у користувача вже є дзвінок |
| `call_not_found` | невідомий `callId` |
| `call_ended` | дзвінок уже завершено |
| `not_allowed` | команда неможлива в поточному стані або для цього учасника |
| `rate_limited` | забагато запитів: не більше 10 `call.invite` за хвилину на користувача |
| `internal` | збій сервера |

## Приклади

### Успішний дзвінок
```
Ірина                      Сервер                       Олена
  │ call.invite(to=Олена) ──▶│                             │
  │◀── ack {call}            │── call.incoming ───────────▶│
  │◀── call.ringing          │                             │
  │                          │◀──────────── call.accept ───│
  │◀── call.connected ───────│── call.connected ──────────▶│
  │        (обидва підключаються до кімнати LiveKit за токеном)
  │ call.hangup ────────────▶│── call.ended(hangup) ──────▶│
  │◀── call.ended(hangup)    │                             │
```

### Без відповіді
```
Ірина                      Сервер                       Олена
  │ call.invite ────────────▶│── call.incoming ───────────▶│
  │◀── call.ringing          │          (60 с тиші)        │
  │◀── call.ended(timeout)   │── call.ended(timeout) ─────▶│
```

### Два пристрої адресата
```
Олена (вкладка A)          Сервер                   Олена (вкладка B)
  │◀── call.incoming ────────│── call.incoming ───────────▶│
  │                          │◀───────────── call.accept ──│
  │◀── call.ended(answered_elsewhere) ─│── call.connected ─▶│
```

## Відповідність дій клієнта
| Дія в `useCallStore` | Команда | Очікуваний стан |
|---|---|---|
| `call(contactId)` | `call.invite` | `ringing` після `ack`, далі `connected` чи `idle` з результатом |
| `cancel()` | `call.cancel` | `idle` після `call.ended` |
| `accept()` | `call.accept` | `connected` після `call.connected` |
| `reject()` | `call.reject` | `idle` |
| `hangup()` | `call.hangup` | `idle` після `call.ended` |
| `toggleHold()` | `call.hold` | `hold` одразу локально, підтверджується `ack` |
| `setSettings({ waiting })` | `settings.update` | значення оновлюється за `ack`, інші пристрої отримують `settings.updated` |
| `acceptWaiting('hold' \| 'end')` | `call.accept` з `action` | другий дзвінок `connected` після `call.connected` |
| `swapCalls()` | `call.hold` з `hold: false` на утримуваному | дзвінки міняються місцями після `call.updated` |

Перехід стору відбувається від подій сервера, а не від власних команд. Виняток: `hold`, бо він локальний і не
змінює стан дзвінка, а при `error` клієнт його відкочує.

## Версіонування
- Поле `v` це версія протоколу. Додавання нових подій і необов'язкових полів не піднімає версію.
- Несумісну зміну робимо як `v: 2`: сервер якийсь час приймає обидві версії, вибір за `v` у `hello`.
- Клієнт, який отримав `error` з кодом `unsupported_version`, показує хосту подію `error` і не перепідключається.

## Рішення
- **Типи тільки TypeScript** у `packages/shared/src/signaling.ts`, без схем і рантайм-валідації через бібліотеки.
  Сервер перевіряє вхідні кадри вручну (обов'язкові поля, типи, розмір).
- **Один інстанс сервера.** Присутність і активні дзвінки живуть у пам'яті процесу. Масштабування на кілька інстансів
  (спільне сховище на кшталт Redis, маршрутизація подій між інстансами) заплановане, але не зараз. Щоб перехід був простим,
  доступ до присутності й активних дзвінків на сервері йде через окремі модулі-сховища, а не через розкидані по коду `Map`.

- **Налаштування задає лише користувач.** Сайт-господар не передає значень за замовчуванням через токен і не може їх заблокувати.

## Відкриті питання
- **Таймер для «Не турбувати».** Автоматичне вимкнення («на годину», «до ранку») як поле `dndUntil`, поки не робимо.
- **Групові дзвінки.** Тут не розглядаємо: кімната LiveKit на двох, контракт розрахований на двох учасників.
