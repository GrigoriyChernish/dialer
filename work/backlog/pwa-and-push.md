# PWA та Web Push сповіщення

Архітектура та специфікація впровадження Progressive Web App (PWA) і Web Push сповіщень для автономного веб-застосунку (`apps/web`).

---

## 1. Загальний огляд і межі задачі

* **Цільове середовище:** На першому етапі — автономний клієнт `apps/web` (розгорнутий на GitHub Pages або власному домені).
* **Стек PWA:**
  * Мінімалістичний `sw.js` у папці `apps/web/public/` без важких сторонніх бібліотек чи генераторів.
  * Маніфест `manifest.webmanifest` з темною темою (`--bg: #0D0F12`), `display: standalone` та набором іконок (192×192, 512×512, maskable).
* **Підтримка платформ:**
  * Android (Chrome, Firefox, Samsung Internet) — підтримка сповіщень та встановлення «з коробки».
  * iOS / iPadOS 16.4+ — Web Push працює штатно після встановлення застосунку на початковий екран («Поділитися» → «На початковий екран»), без нав'язливих попапів.
  * Десктоп (Chrome, Edge, Safari, Firefox).

---

## 2. Життєвий цикл та сценарії Push-сповіщень

| Подія на сервері | Дія Service Worker у `sw.js` | Що бачить і чує користувач |
| :--- | :--- | :--- |
| **Вхідний дзвінок** (`call.invite`) | Перевіряє через `clients.matchAll()`, чи є сфокусоване вікно. Якщо вікно відкрито — пуш ігнорується (дзвінок показує сам UI). Якщо всі вікна згорнуті або закриті — викликає `registration.showNotification()` | Системний банер: «Вхідний дзвінок від {Ім'я}», вібрація `[500, 250, 500, ...]`, `requireInteraction: true`, кнопки дій **«Відповісти»** та **«Відхилити»** |
| Клік **«Відповісти»** | Відкриває або фокусує вікно (`clients.openWindow('/')`), передаючи параметр автоприйняття (наприклад, `#/call?action=accept&callId=...`) | Відкривається застосунок одразу на екрані розмови |
| Клік **«Відхилити»** | Виконує тихий фоновий `fetch` на сервер (`POST /api/call/reject`) і закриває сповіщення. Вікно браузера **не відкривається** | Сповіщення миттєво зникає, у того, хто дзвонить, гудки припиняються зі статусом `busy` |
| **Дзвінок скасовано або минув таймаут** | Сервер надсилає пуш про завершення. SW знаходить активне сповіщення за `tag: callId`, закриває його і показує нове сповіщення | Банер замінюється на «Пропущений дзвінок від {Ім'я}» |
| **Дзвінок прийнято на іншому пристрої** | Сервер надсилає пуш про перехоплення. SW знаходить активне сповіщення за `tag: callId` і тихо закриває його | Сповіщення тихо зникає без створення запису «пропущений» |

## 3. Керування підпискою в Налаштуваннях (`SettingsPage`)

Підписка на сповіщення **не нав'язується автоматично**, а свідомо вмикається користувачем у налаштуваннях застосунку:

* **Перемикач у `SettingsPage.vue`:**
  * Пункт: «Сповіщення про дзвінки»
  * Підказка: «Коли вкладку закрито · лише цей пристрій»
  * Іконка: `bell`
* **Сценарій увімкнення:**
  1. Користувач перемикає тумблер у положення «Увімкнено».
  2. Застосунок перевіряє статус дозволів у браузері. Якщо дозвіл ще не запитувався (`default`), викликається `Notification.requestPermission()`.
  3. Якщо користувач дав дозвіл (`granted`), сервіс-воркер створює підписку `registration.pushManager.subscribe(...)` із VAPID-ключем сервера (який прийшов у `hello.ok`).
  4. Клієнт надсилає команду сигналізації `push.subscribe`:

     ```json
     {
       "type": "push.subscribe",
       "subscription": { ... }
     }
     ```

  5. Стан зберігається в локальних налаштуваннях пристрою (`prefs.pushEnabled = true`).
* **Сценарій вимкнення:**
  1. Користувач вимикає тумблер.
  2. Клієнт відписує сервіс-воркер локально (`subscription.unsubscribe()`).
  3. Клієнт надсилає серверу команду `push.unsubscribe` (видаляє запис із таблиці `push_subscriptions`).
  4. Стан оновлюється (`prefs.pushEnabled = false`).
* **Обробка блокування (`denied`):**
  * Якщо користувач заблокував сповіщення в налаштуваннях браузера, тумблер блокується або вимикається, а підказка змінюється на «Заблоковано в налаштуваннях браузера».

## 4. Взаємодія з бекендом (`apps/server`)

### А. VAPID ключі

1. Сервер генерує або бере зі змінних оточення пару VAPID-ключів (`VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`).
2. Публічний ключ передається клієнту у відповіді `hello.ok`:

   ```json
   {
     "type": "hello.ok",
     "vapidPublicKey": "BEl62iUYgUivxIkv69yViEuiBIa-Ib9-Skv..."
   }
   ```

### Б. База даних сервера (`apps/server`)

Таблиця підписок у SQLite:

```sql
CREATE TABLE IF NOT EXISTS push_subscriptions (
  user_id TEXT NOT NULL,
  device_id TEXT NOT NULL,
  endpoint TEXT NOT NULL,
  p256dh TEXT NOT NULL,
  auth TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  PRIMARY KEY (user_id, device_id)
);
```

### В. Відправка Push-сповіщень на бекенді

* Використовується бібліотека `web-push`.
* При створенні дзвінка (`call.invite`) сервер надсилає push на всі збережені підписки адресата.
* Тихий ендпоінт для відхилення з фону SW: `POST /api/call/reject` з валідацією токена дзвінка.

## 5. Зафарбовування статус-бару під тему (`theme-color`)

Для відчуття нативного застосунку колір статус-бару та верхньої панелі браузера (Chrome Android, Safari iOS) має безшовно збігатися з фоном поточної теми (`--bg` з дизайн-системи):

* **Кольори теми:**
  * Світла тема: `#eef0f6` (значення `--bg` для світлої теми)
  * Темна тема: `#0a0c14` (значення `--bg` для темної теми)
* **Статичні мета-теги в `index.html`:**
  * Системне перемикання для початкового завантаження через атрибут `media`:
    ```html
    <meta name="theme-color" content="#eef0f6" media="(prefers-color-scheme: light)" />
    <meta name="theme-color" content="#0a0c14" media="(prefers-color-scheme: dark)" />
    <meta name="apple-mobile-web-app-capable" content="yes" />
    <meta name="apple-mobile-web-app-status-bar-style" content="black-translucent" />
    ```
* **Динамічна синхронізація в `entries/app.ts`:**
  * Коли користувач змінює тему вручну в налаштуваннях (`theme: 'light' | 'dark'`), вотчер теми в `app.ts` динамічно оновлює мета-тег `theme-color`:
    * Для `'light'` встановлює колір `#eef0f6`.
    * Для `'dark'` встановлює колір `#0a0c14`.
    * Для `'auto'` відновлює прив'язку до системного `prefers-color-scheme`.
* **Інтеграція в PWA Manifest (`manifest.webmanifest`):**
  * Вказати `background_color` та `theme_color` (базовий темний `#0a0c14` або світлий).
* **Мобільний лейаут і безпечні зони:**
  * Завдяки вже наявному `viewport-fit=cover` та використанню `--bg` на `<body>`, фон екрана затікає під вирізи й статус-бар без різких меж (з урахуванням `env(safe-area-inset-top)`).

## 6. Етапи реалізації

1. **Клієнт (PWA, Налаштування та теми):**
   * Створити `manifest.webmanifest` з іконками й кольорами теми.
   * Додати підтримку адаптивного статус-бару: мета-теги `theme-color` у `index.html` та синхронізація з `prefs.theme` у `entries/app.ts`.
   * Підключити реєстрацію `sw.js` у `apps/web/src/entries/app.ts`.
   * Реалізувати базовий `apps/web/public/sw.js` (обробники `push` та `notificationclick`).
   * Додати тумблер керування сповіщеннями в `SettingsPage.vue` з локальним збереженням стану (`usePrefsStore`).
2. **Бекенд (Сервер):**
   * Додати підтримку VAPID та таблицю `push_subscriptions` у `apps/server`.
   * Реалізувати команди сигналізації `push.subscribe` та `push.unsubscribe`.
   * Додати диспетчеризацію Web Push для подій дзвінка (`invite`, `cancel`, `timeout`, `taken`).
   * Додати легкий HTTP-ендпоінт для фонового відхилення дзвінка.
3. **Тестування:**
   * Локальна перевірка через Chrome DevTools (симуляція Push-подій).
   * Перевірка зміни кольору статус-бару при перемиканні теми ('light' / 'dark' / 'auto').
   * Тестування на реальному Android-пристрої та iOS PWA.
