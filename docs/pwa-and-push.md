# PWA та Web Push сповіщення

Специфікація PWA і Web Push для автономного застосунку `apps/web`. Роботу поділено на три етапи, кожен розгортається окремо:

| Етап | Зміст | Стан |
| :--- | :--- | :--- |
| **A** | Маніфест, іконки, `theme-color` | реалізовано |
| **B** | Підписка в Налаштуваннях, `push_subscriptions`, VAPID, `sw.js` | реалізовано |
| **C** | Дзвінок до адресата без мережі, дії «Відповісти» / «Відхилити» | реалізовано |

**Межі.** Лише Android (Chrome та сумісні браузери). iOS відкладено: Web Push там потребує встановленого застосунку, не підтримує кнопки дій і вібрацію, тому окремих рішень для нього поки немає. Віджет (`widget.html`) поза межами: він живе в `iframe` на чужому сайті, і сервіс-воркер має бути на origin сайту-господаря (див. пункт 8 у [беклозі](../work/backlog/backlog.md)).

## Етап A. PWA і колір статус-бару

### Маніфест і іконки

Файли в `apps/web/public/` (Vite копіює їх у корінь збірки):

- `manifest.webmanifest`: `name` «Дзвонілка», `display: standalone`, `start_url: '.'`, `scope: '.'` (відносні шляхи, бо на GitHub Pages застосунок живе в `/dialer/`), `background_color` і `theme_color` темні.
- `icons/icon-192.png`, `icons/icon-512.png` і `icons/maskable-512.png` (значок слухавки на фоні `--bg` темної теми, для maskable контент у безпечній зоні 80 %). Генерує `scripts/make-icons.mjs` без залежностей.

Сервіс-воркера на етапі A немає: застосунок не працює офлайн, Chrome на Android пропонує встановлення і без нього.

### `theme-color`

Колір статус-бару й верхньої панелі браузера збігається з `--bg` поточної теми ([`tokens.css`](../apps/web/src/app/styles/tokens.css)).

- У `index.html` дві мета-теги з `media="(prefers-color-scheme: …)"`: світла `#eef0f6`, темна `#0a0c14`. Вони діють до запуску скриптів.
- `applyTheme(theme)` ([`shared/theme.ts`](../apps/web/src/shared/theme.ts)) разом із темою веде й колір статус-бару, викликається вотчером `prefs.theme` в `entries/app.ts`:
  - `light` / `dark`: пара з `media` прибирається, ставиться один тег без `media` з відповідним кольором (інакше системна тема перебила б вибір користувача);
  - `auto`: пара з `media` повертається.
- `theme_color` у маніфесті статичний (темний): вирішальне слово за мета-тегами.

## Етап B. Підписка і сервер

### Підписка в Налаштуваннях (`SettingsPage`)

Підписка не нав'язується, користувач вмикає її тумблером (рядок «Сповіщення про дзвінки», підказка «Коли закрито · цей пристрій», іконка `bell-ring`). Дизайн: `Flow · Settings` (`Settings`, `Settings · notifications on`, `· notifications blocked`).

1. Дозвіл `default` → `Notification.requestPermission()`.
2. `granted` → `registration.pushManager.subscribe({ userVisibleOnly: true, applicationServerKey })`, ключ зі `hello.ok.vapidPublicKey`.
3. Клієнт надсилає `push.subscribe` з підпискою; вимкнення: `subscription.unsubscribe()` + `push.unsubscribe`.
4. Стан тумблера береться з `pushManager.getSubscription()`, а не з локальних налаштувань (інакше розійдуться).
5. `denied`: тумблер недоступний, підказка «Заблоковано в браузері» кольору `warn`.
6. Рядка немає, якщо браузер не вміє push (`serviceWorker`, `PushManager`, `Notification`) або сервер не віддав `vapidPublicKey`. Помилка підписки: підказка «Не вдалося увімкнути».
7. Поки підписка зберігається (дозвіл уже дано: реєстрація сервіс-воркера, `pushManager.subscribe`, `push.subscribe` на сервер), поверх екрана під затемненням показано попап зі спінером «Вмикаємо сповіщення…» (`usePush().saving`). Системний запит дозволу попап не перекриває: він з'являється лише після `granted` і зникає при успіху чи помилці.

Логіка живе в `features/settings/push.ts` (`usePush`). Якщо сервер змінив ключ VAPID, стара підписка знімається й створюється нова.

При виході підписка знімається лише на сервері (`SettingsPage.logout` → `usePush().release`, не довше за секунду), тож після виходу дзвінки не приходять. У браузері вона лишається разом із власником (`localStorage` `dialer.push.owner`, `userId` того, хто ввімкнув), і після повторного входу того самого користувача вмикати заново не треба. Після кожного завантаження сторінки і `hello.ok` застосунок повторно віддає серверу наявну підписку (`resyncPush`), але лише її власнику: сервер міг її втратити, а підписка з тим самим `endpoint` переходить до поточного користувача. Інший користувач цього браузера бачить тумблер вимкненим і не отримує чужих дзвінків, поки не ввімкне сам (тоді власником стає він). Вимкнення тумблером знімає підписку й у браузері, і власника. Підписка без запису власника (з версії до цієї зміни) дістається тому, хто увійшов.

### Сервіс-воркер

`apps/web/public/sw.js` реєструється відносним шляхом `sw.js?server=…` (на Pages це `/dialer/sw.js`, область `/dialer/`) при вмиканні сповіщень. Без кешування й `fetch`. Він показує «Вхідний дзвінок» (`tag: callId`, `requireInteraction`, кнопки «Відповісти» і «Відхилити») на `call.incoming`, замінює його на «Пропущений дзвінок» на `call.ended` з `missed` чи закриває на `call.ended`, а натискання й «Відповісти» фокусують вікно застосунку чи відкривають `registration.scope` (для «Відповісти» з `callId`, див. етап C). Перевірка без сервера: DevTools → Application → Service Workers → Push з тілом `{"type":"call.incoming","callId":"c1","from":{"name":"Олена"}}`.

**Оновлення воркера.** Браузер сам перевіряє `sw.js` при відкритті застосунку й при push (не частіше ніж раз на добу), нова версія вмикається одразу (`skipWaiting`, `clients.claim`), перезавантаження не треба: воркер не кешує сторінки. Щоб PWA, яку довго не закривають, теж оновлювалась, застосунок викликає `updateWorker` (`features/settings/push.ts`), лише якщо воркер уже зареєстровано: при старті реєструє його повторно (так до `sw.js?server=…` доходить нова адреса сервера), а при поверненні на екран викликає `registration.update()` не частіше ніж раз на 10 хв.

### Сервер

- Таблиця `push_subscriptions` (міграція `006_push_subscriptions.sql`): `endpoint` (ключ), `user_id`, `site_id`, `device_id`, `p256dh`, `auth`, `created_at`; зовнішній ключ на користувача з каскадним видаленням.
- Ключі VAPID лише зі змінних `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` (секрети Fly; пару створює `web-push generate-vapid-keys`). Генерація на льоту заборонена: після перезапуску всі підписки стали б недійсними. Без ключів push вимкнено, частково задані ключі — помилка конфігурації.
- Відправка: бібліотека `web-push`, інтерфейс `PushSender` (у тестах підміняється). Відповідь `404` / `410` видаляє підписку.
- **Безпека.** Сервер сам робить HTTP-запит на endpoint із підписки, тож endpoint перевіряється: `https` і хости відомих push-сервісів (FCM, Mozilla, WNS); інакше це SSRF.

## Етап C. Дзвінок до адресата без мережі

Без push дзвінок до адресата, в якого немає жодного пристрою в мережі, одразу завершувався з `offline`. Тепер:

- адресат має підписки → дзвінок лишається `ringing` без WebSocket адресата, `offline` лише без підписок;
- після `hello` адресата очікуваний дзвінок приходить у `hello.ok.calls`;
- push надсилається на пристрої **без активного WebSocket або з прихованим вікном** (`device.visibility`: Android заморожує PWA у фоні, а сервер закриває сокет лише після хвилини тиші). Пристрій із видимим вікном push не отримує; якщо push усе ж прийшов, коли вікно вже на екрані, воркер сповіщення не показує (Chrome цього не вимагає для видимої сторінки).

| Подія на сервері | Сповіщення |
| :--- | :--- |
| Вхідний дзвінок | заголовок «{Ім'я}», текст «Вхідний дзвінок», кнопки **Відповісти** / **Відхилити**, `requireInteraction`, `tag: callId`, `TTL` = залишок таймауту, `urgency: high` |
| `cancelled` / `timeout` | сповіщення з тим самим `tag` замінюється на «Пропущений дзвінок» з ім'ям у тексті |
| інші завершення (`answered_elsewhere`, `rejected` тощо) | сповіщення закривається |

- **Відповісти:** дзвінок приймається одразу, без екрана підтвердження. Воркер фокусує наявне вікно й шле йому `postMessage({ type: 'answer', callId })`, або відкриває `registration.scope` і тримає `callId` до 30 с, поки нове вікно не спитає `answer.pending`. Застосунок (`listenAnswer` → `call.answerFromPush`) приймає дзвінок, щойно той з'явиться (у сокеті чи `hello.ok.calls`), чекаючи не довше за хвилину. Другий вхідний під час розмови не приймається сам: «утримати» чи «завершити» вирішує користувач. `callId` не йде посиланням: інакше чуже посилання вмикало б камеру й мікрофон.
- **Натискання на сповіщення** (не на кнопку) відкриває застосунок з екраном вхідного дзвінка, відповідає користувач.
- **Відхилити:** фоновий `POST /push/reject` з токеном із payload (воркер не бачить `localStorage`), дзвінок завершується з `rejected`. Вікно не відкривається. Адресу сервера воркер бере з параметра реєстрації `sw.js?server=…`. Деталі та формат: [сигналізація](signaling.md#post-pushreject).
- Це сповіщення, а не гудки: закритий застосунок мелодію не відтворює.
